## 3. Release configuration review

- **`eas.json`:** every profile pins `APP_ENV` (now enforced by a test). Only `development` sets `developmentClient`. `appVersionSource: remote`, and production uses `autoIncrement`. No signing material or secrets are in the repository, and `.gitignore` excludes `*.jks`, `*.p8`, `*.p12`, `*.key` and `*.mobileprovision`.
- **Environment variables:** only public `EXPO_PUBLIC_*` identifiers are used. `.env.example` uses `.invalid` placeholders and says never to add a client secret. Production config fails closed without a complete Auth0 configuration. CI E2E sets `EXPO_NO_DOTENV=1`.
- **GitHub Actions:**
  - `permissions: contents: read` everywhere.
  - The release gate runs in a protected `release-acceptance` environment.
  - No secrets are referenced.
  - Actions are pinned to major tags, not SHAs (hardening opportunity, not a blocker).
  - Maestro is installed with `curl | bash` at a pinned version (supply-chain note).
- **Debug and development flags in release:** the expo-dev-client scheme `exp+mobile-app` is still registered in release builds, both as an Android intent filter and an iOS URL scheme. Impact is low: those URLs resolve to `unknown` in `parseDeepLinkUrl`. Recommended follow-up: pass `addGeneratedScheme: false` to expo-dev-client for non-development builds. The prebuild entitlements carry `aps-environment=development`; EAS/Xcode export sets the distribution value, so this needs checking on the first signed build.
